# CLAUDE.md — LOOP Contractor MVP

Guidance for Claude Code (and humans) working in this repository. Read this before making changes.

## What LOOP is

LOOP is a UK IT contractor network that keeps contractor skills, availability and preferences **live and confirmed**. The MVP is contractor-first: CV upload → AI profile → verify → register → availability → preferences → go LIVE → My LOOP, plus email reconfirmation reminders ("Stay Current"), referrals ("Introduce Contractors"), Founding Contractor qualification and a rewards ledger. Agency access, matching and payouts are built behind feature flags and are **not** live.

Source of truth for requirements: *LOOP Contractor MVP V2.0 Master Developer Handover* (11 Oct 2026). Spec section references (A1–A16, B1–B12, C1–C3) are used in code comments and PRs.

## Stack

- **Monorepo:** pnpm workspaces + Turborepo, TypeScript strict, Node 24 LTS (`.nvmrc`).
- **API:** NestJS 11, REST + OpenAPI (`@nestjs/swagger`), validation with `nestjs-zod`. Single app serves the API (`/api/v1`), the prebuilt web and admin bundles, and runs background jobs.
- **Jobs:** pg-boss (Postgres-backed). No Redis.
- **Database:** PostgreSQL + Prisma. Raw SQL (TypedSQL / `$queryRaw`) only where locking is required.
- **Web:** React 19, React Router v7 (framework mode, landing page prerendered), TanStack Query hooks generated by Orval, React Hook Form + Zod, Tailwind + shadcn/ui.
- **Admin:** React 19 + Vite SPA, TanStack Table.
- **Integrations:** LLM API for CV extraction, Postmark/SES (email), S3-compatible storage + malware scan, Wise (payouts, disabled).
- **Deploy:** one Docker image, `APP_ROLE=all|api|worker`, AWS eu-west-2 (ECS Fargate, RDS, S3, Secrets Manager) via AWS CDK in `infra/`.

## Commands

```bash
pnpm install                 # install all workspaces
docker compose up -d         # local Postgres, MinIO (S3), Mailpit, ClamAV
pnpm db:migrate              # prisma migrate dev
pnpm db:seed                 # seed dev data (test contractors, flags)
pnpm dev                     # api + web + admin in watch mode
pnpm api:generate            # regenerate OpenAPI spec + Orval client (run after any API change)
pnpm lint && pnpm typecheck  # must pass before commit
pnpm test                    # unit + integration (Vitest, Testcontainers)
pnpm e2e                     # Playwright acceptance tests (spec C2)
pnpm build && docker build . # production image
```

Run a single package with `pnpm --filter <name> <script>` (e.g. `pnpm --filter @loop/domain test`).

## Architecture rules (do not break these)

1. **Business rules live in `packages/domain`.** Availability colour, freshness schedules, founding eligibility, reward eligibility and referral validity are pure functions with unit tests. Controllers and job handlers call them; they never re-implement them.
2. **Dependency direction:** `apps/*` → `packages/*`. `domain` depends on nothing internal. `contracts` depends only on `zod`. Nest modules talk to each other through exported services, never by reaching into another module's Prisma models directly.
3. **Separate dimensions, never one status field** (B2). Employment situation, availability facts, freshness (`lastConfirmedAt`, `confirmationSource`) and visibility (`live`, `paused`, `searchSuppressed`) are stored independently. **Colour is derived**, cached only for search, and recomputed by the freshness sweep.
4. **Never auto-promote to green** when a contract end date passes (B3). Unconfirmed → grey.
5. **Permanent employees stay blue** regardless of notice length.
6. **AI never invents data** (A4). Every extracted field must carry a source excerpt found in the CV text and a confidence score; fields without evidence are dropped. AI output is stored in `ExtractionRun`, separate from contractor-confirmed values.
7. **Never silently overwrite contractor-confirmed data** (A5). New CV uploads create suggestions.
8. **Founding allocation is transactional** (B6): conditional counter update + insert in one transaction. Never count-then-insert.
9. **Rewards are created exactly once** (C2): unique key on (type, beneficiary, qualifying contractor). Use idempotency keys on mutating endpoints.
10. **No agency verification → no reward approval** (B7). Payout code paths stay behind the `payouts.live` feature flag.
11. **Profit-sharing percentages are not hardcoded** (B10). Store eligibility only.
12. **Every change to contractor, referral, reward or payment data writes an `AuditEvent`** (who, what, when, before/after).
13. **Business rules return computed status to clients.** Web, admin and the future app never calculate colour themselves.
14. **API is versioned** under `/api/v1`. Only backward-compatible changes within a version (future mobile clients cannot be force-updated instantly).

## Coding conventions

- TypeScript strict; no `any`, no non-null assertions without a comment explaining why.
- Request/response shapes are Zod schemas in `packages/contracts`; DTOs derive from them. After changing an endpoint, run `pnpm api:generate` and commit the generated client.
- Prisma: one migration per change, descriptive names (`add_referral_attribution`). Never edit an applied migration. Money is stored as integer pence.
- Dates: store UTC (`timestamptz`); compute date-only rules (availability, contract end) in `Europe/London` via `packages/domain` helpers.
- Nest DI: always inject constructor dependencies with an explicit `@Inject(Token)` (e.g. `constructor(@Inject(MeService) private readonly me: MeService) {}`). `tsx` (dev) and Vitest use esbuild, which does not emit `design:paramtypes`, so implicit injection yields `undefined` at runtime and a 500.
- Errors: throw typed domain errors; the global filter maps them to RFC 9457 problem responses.
- Jobs: one handler per job name in `apps/api/src/jobs`, idempotent, with retry limits. Scheduled sweeps use pg-boss singleton keys.
- Frontend: feature folders under `app/features/*`; server state only via generated hooks; status colour always rendered with label + icon (`<AvailabilityBadge>`).
- Names: files `kebab-case.ts`, classes `PascalCase`, Zod schemas `XxxSchema`, types inferred `type Xxx = z.infer<typeof XxxSchema>`.

## Testing expectations

- Any change in `packages/domain` needs table-driven Vitest tests covering the spec rules it touches (B3, B4, B6, B7).
- New endpoints need an integration test (Nest + Testcontainers Postgres).
- Spec C2 acceptance tests live in `apps/e2e` and must stay green.
- Concurrency test for founding allocation must pass (parallel completions never exceed the cap).

## Security and privacy

- Never log CV content, phone numbers, emails or tokens. Use the logger's redaction list; add new sensitive fields to it.
- Never commit secrets. Config comes from env (validated by `apps/api/src/config`); production secrets from AWS Secrets Manager.
- Auth: web uses httpOnly `SameSite=Lax` cookies + CSRF token; sign-in is passwordless email OTP (ADR 0002). OTPs, one-touch links and session tokens are stored as SHA-256 hashes only. Bearer/refresh tokens for the app are deferred (ADR 0003).
- OTP endpoints are rate-limited per phone, IP and device; UK numbers only.
- Webhooks (email provider, Wise) must verify provider signatures.
- Reminders are email-only; routine SMS is removed from the MVP. Operational and marketing consent are separate; respect both.
- Personal data stays in the UK region. Retention and erasure go through the `privacy` module.

## Working agreements for Claude

- Prefer small, focused changes; keep each PR to one spec area and reference its section (e.g. "B4 freshness: orange window checks").
- Before editing, read the relevant module and its domain tests. Follow existing patterns over inventing new ones.
- Run `pnpm lint && pnpm typecheck && pnpm test` before declaring work done; run `pnpm e2e` when touching user journeys.
- Do not add new runtime dependencies or infrastructure (e.g. Redis, a second service) without flagging it.
- Do not enable feature flags for payouts, profit sharing or agency access in code or seeds for production.
- If the spec is ambiguous, check "Open questions" in the plan doc; don't guess silently — leave a `TODO(spec):` comment and mention it.

## Domain glossary

| Term | Meaning |
| --- | --- |
| LIVE | Profile activated and visible (subject to visibility flags) |
| Lime green (Available Now) | Confirmed available now; reconfirm every 7 days |
| Orange | Contract ending within 28 days; prompts at 28/14/7 days before end, an end-date outcome ask, then +3/+7 days if unanswered |
| Red | Unavailable beyond 28 days; reconfirm every 30 days |
| Blue (Permanently Employed) | Permanently employed, open to contracting; reconfirm every 60 days |
| Grey | Availability unconfirmed; follow-up, then manual call, then search suppression |
| Freshness | Date and source of the last meaningful confirmation |
| Founding Contractor | One of the first 50,000 to be current with 5 unique registered direct referrals |
| Qualifying contract | First LOOP contract with 3 months of agency-verified paid service |
